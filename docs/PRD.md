## Problem Statement

Consumer Packaged Goods (CPG) suppliers generate billions of dollars in surplus inventory (overproduced or short-dated stock) that frequently goes to waste. The process of liquidating this inventory is slow and inefficient. Suppliers send stock lists and invoices in wildly inconsistent, unstructured formats (PDFs, messy CSVs), requiring slow manual data entry. Additionally, deciding how much to discount soon-to-expire goods is done by "gut instinct," and matching these batches to the right retail buyers leads to either spamming buyers or missing sales.

## Solution

Build the **Spoiler Alert Inventory Platform**—a B2B surplus liquidation portal containing:

### 1. Core Product-Grade Features (AI-Driven)
- **Hybrid Ingestion Engine**: Extracts tabular data from PDFs using IBM Docling, applies fuzzy matching on headers, and provides a B2B self-serve column mapping wizard to define layout templates.
- **AI Normalization Engine**: Uses a Gemini LLM to clean messy names and normalize attributes (sizes, units, packaging).
- **Dynamic Yield Optimization Engine**: Runs a mathematical pricing simulator in Python to dynamically calculate the optimal discount using `scipy.optimize` based on expiration urgency, stock volume, and category-specific price elasticity.
- **Demand Matching Engine**: Ranks and pairs newly ingested inventory with the top 5 retail buyers based on semantic profile preferences and historical transaction logs.
- **Interactive Dashboard UI**: Consolidates these modules in a modern dark-mode frontend built with TypeScript and Vanilla CSS.

### 2. Simulated/Minimum-Support Features
- **Competitive Bidding**: Allows sellers to publish listing offers for bidding, automatically generating simulated buyer bids that can be reviewed and awarded.
- **Alternative Disposal (Donation & Recycling)**: Simulates the redirection of unsold surplus to registered food banks or recycling centers with simulated logs for transport coordination.
- **Post-Sale Analytics**: Provides decision intelligence views displaying pre-computed metrics for COGS recovery rate, Remaining Shelf Life (RSL), leftover tracking, and landfill diversion.

## User Stories

### Core AI-Powered Workflows
1.  As a CPG Supplier, I want to upload a messy PDF invoice of surplus inventory, so that I don't have to manually copy and paste details into the database.
2.  As a CPG Supplier, I want the system to automatically guess column mappings (e.g. matching "QTY (Cases)" to `quantity`), so that I don't have to configure column mappings for standard structures.
3.  As a CPG Supplier, I want to see a visual preview of my parsed document, so that I can inspect the values before ingestion.
4.  As a CPG Supplier, I want a drag-and-drop mapping wizard to manually correct columns if the auto-mapping is uncertain, so that I can guarantee the mapping accuracy.
5.  As a CPG Supplier, I want my manual column configuration saved as a "Supplier Template," so that future uploads with the same layout are ingested instantly and automatically.
6.  As a CPG Supplier, I want the system to normalize messy product names (e.g., converting "Ktchp 24oz" to `Tomato Ketchup` and extracting `24oz` as the packaging size), so that our product listings are clean and search-friendly.
7.  As a Platform Administrator, I want to see all active surplus inventory items in a central dashboard, so that I can track their liquidation status.
8.  As a Platform Administrator, I want to see a visual countdown timer indicating the days remaining until expiration for each item, so that I know which products need urgent attention.
9.  As a Platform Administrator, I want to adjust volume and expiration sliders in an interactive pricing simulator, so that I can see the impact of decay on suggested pricing recommendations in real-time.
10. As a Platform Administrator, I want the dynamic discount engine to scale discounts exponentially as the expiration date approaches, so that we clear inventory before it spoils.
11. As a Platform Administrator, I want the pricing engine to discount bulk quantities deeper, so that we incentivize wholesale buyer volumes.
12. As a Platform Administrator, I want to view the top 5 matched retail buyers for any surplus batch, so that I target high-probability deals immediately.
13. As a Platform Administrator, I want to see a match breakdown explaining why a buyer was recommended (e.g., "accepts short-dated dairy, purchased Kraft Heinz 3 times before"), so that I have context before reaching out.

17. As a CPG Supplier, I want to view active bids for a listing and click "Award" to complete the sale, automatically updating inventory status and writing transaction logs.
18. As a CPG Supplier, I want to divert short-dated stock to "Donation" or "Recycling" via embedded actions, so that I can coordinate transport with a food bank or recycler and verify cost savings on landfill fees.

## Implementation Decisions

### 1. High-Level Architecture & Bounded Contexts
The application is structured into four distinct bounded contexts:
- **Inventory Intelligence**: Ingestion, template mapping, product master creation, and risk assessment.
- **Disposition Management**: Opportunities, yield pricing recommendations, and decision logs (DDD: Sell, Donate, Recycle, Destroy).
- **Marketplace & Fulfillment**: Marketplace listings, semantic buyer matching, bidding execution, awards, and shipments.
- **Analytics & Sustainability**: Real-time KPI aggregation and snapshot storage.

The **Node.js Express** app acts as the orchestrator and database client, while the **FastAPI Python sidecar** performs CPU-heavy tasks: Docling table extraction, dynamic pricing optimization, and semantic buyer embedding similarity scoring.

---

### 2. API Data Transfer Objects (DTOs)

#### Ingestion Context:
*   **`POST /api/ingest/upload`**
    *   *Request*: `multipart/form-data` containing `file` (.pdf or .csv).
    *   *Response (200 OK)*:
        ```json
        {
          "documentId": "doc_123456",
          "fileName": "invoice_unilever_july.pdf",
          "rawGrid": [["SKU", "Desc", "Cases", "Exp Date", "Unit Cost"], ["UN-88", "Dairy Creamer", "450", "2026-08-01", "12.50"]],
          "suggestedMapping": { "sku": "SKU", "description": "Desc", "quantity": "Cases", "expirationDate": "Exp Date", "originalPrice": "Unit Cost" }
        }
        ```
*   **`POST /api/ingest/confirm`**
    *   *Request*:
        ```json
        {
          "documentId": "doc_123456",
          "supplierId": "supp_789",
          "mappings": { "sku": "SKU", "description": "Desc", "quantity": "Cases", "expirationDate": "Exp Date", "originalPrice": "Unit Cost" },
          "saveTemplate": true,
          "templateName": "Unilever Standard Layout"
        }
        ```
    *   *Response (200 OK)*:
        ```json
        {
          "countImported": 12,
          "lotIds": ["lot_aaa111", "lot_bbb222"]
        }
        ```

#### Disposition Context:
*   **`POST /api/inventory/lot/:id/assess-risk`**
    *   *Response (200 OK)*: Returns the created `InventoryRisk` and `Opportunity` documents.
*   **`POST /api/inventory/opportunity/:id/pricing/recommend`**
    *   *Request*: `{ "daysRemaining": 15, "quantity": 450 }`
    *   *Response (200 OK)*: Returns the updated `PricingRecommendation` object including the price decay curve metrics.

#### Marketplace Context:
*   **`POST /api/marketplace/listing/create`**
    *   *Request*: `{ "opportunityId": "opp_999", "allowBidding": true, "buyerSegment": "National Wholesaler" }`
    *   *Response (201 Created)*: The `MarketplaceListing` object.
*   **`GET /api/marketplace/listing/:id/matches`**
    *   *Response (200 OK)*: `{ "matches": [ { "buyerId": "buyer_1", "score": 0.94, "rank": 1, "reasons": ["Dairy pref", "Within 30mi"] } ] }`
*   **`POST /api/marketplace/listing/:id/bids`**
    *   *Request*: `{ "buyerId": "buyer_1", "quantity": 100, "price": 9.50 }`
    *   *Response (201 Created)*: The created `Offer` (Bid) document.

### 3. FastAPI Sidecar RPC Method Interfaces (Node.js $\rightarrow$ Python)

*   **`POST /parse-document`**
    *   *Input*: Multipart `file`
    *   *Output*: `{ "tables": [ { "name": "Table_0", "headers": ["SKU", "Desc"], "rows": [["UN-88", "Dairy Creamer"]] } ] }`
*   **`POST /suggest-pricing`**
    *   *Input*: `{ "days_remaining": 15, "quantity": 450, "original_price": 12.50, "category": "Dairy" }`
    *   *Output*:
        ```json
        {
          "recommended_discount": 0.35,
          "recommended_price": 8.125,
          "expected_sell_through": 0.85,
          "expected_revenue": 3108.12,
          "elasticity": -1.45
        }
        ```
*   **`POST /recommend-buyers`**
    *   *Input*: `{ "product_name": "Dairy Creamer", "category": "Dairy", "supplier_id": "supp_789", "distance_matrix": { "buyer_1": 25.5, "buyer_2": 150.0 } }`
    *   *Output*:
        ```json
        {
          "matches": [
            { "buyer_id": "buyer_1", "score": 0.94, "rank": 1, "reasons": ["Dairy Match", "Under 50 miles"], "distance": 25.5 }
          ]
        }
        ```

### 4. Database Collections (MongoDB Mongoose Schemas)

1.  **`Supplier`**: `{ _id, name, companyCode, preferredDisposition, active, createdAt }`
2.  **`DistributionCenter`**: `{ _id, supplierId, name, code, address, coordinates: { lat, lng }, coldStorage: boolean }`
3.  **`ProductMaster`**: `{ _id, supplierId, sku, gtin, brand, category, subCategory, description, shelfLifeDays }`
4.  **`InventoryLot`**: `{ _id, supplierId, distributionCenterId, productId, lotNumber, productionDate, expirationDate, remainingShelfLife, quantityCases, availableQty, costPerCase, standardSellPrice, status: 'pending'|'active'|'sold'|'expired'|'donated'|'recycled' }`
5.  **`InventoryRisk`**: `{ lotId, riskScore, daysRemaining, velocityScore, riskCategory, predictedWaste, lastEvaluated }`
6.  **`Opportunity`**: `{ lotId, opportunityType: 'sell'|'donate'|'recycle'|'destroy', priority, recommendedAction, status: 'draft'|'approved'|'completed' }`
7.  **`PricingRecommendation`**: `{ lotId, recommendedDiscount, recommendedPrice, expectedSellThrough, expectedRevenue, elasticity }`
8.  **`MarketplaceListing`**: `{ opportunityId, sellerId, allowBidding, startingPrice, minimumPrice, status: 'active'|'closed', expiresAt }`
9.  **`Buyer`**: `{ _id, companyName, acceptsShortDated, minShelfLife, categories: [String], transportRadius, warehouseLocations: [{ lat, lng }] }`
10. **`BuyerMatch`**: `{ lotId, buyerId, score, rank, reasons: [String], distance }`
11. **`Offer`**: `{ listingId, buyerId, quantity, price, status: 'pending'|'accepted'|'rejected', submittedAt }`
12. **`Award`**: `{ listingId, offerId, buyerId, awardedQty, price, approvedDate }`
13. **`Shipment`**: `{ awardId, carrier, pickupLocation, deliveryLocation, status: 'scheduled'|'in_transit'|'delivered', temperature }`
14. **`Donation`**: `{ lotId, foodBankName, quantity, taxBenefit, landfillAvoided, co2Saved, pickupDate }`
15. **`Disposal`**: `{ lotId, method: 'recycle'|'destroy', facility, landfillFee, recyclingFee, completedDate }`
16. **`SupplierTemplate`**: `{ supplierId, templateName, columnMappings: Map, headerAliases: Map }`
17. **`DocumentImport`**: `{ supplierId, fileName, checksum, status: 'uploaded'|'parsed'|'imported'|'error', recordsParsed, errors: [String] }`
18. **`AnalyticsSnapshot`**: `{ supplierId, date, recoveryRate, sellThrough, wasteAvoidedTons, landfillSavings, co2Savings }`
19. **`LiquidationAutomation`**: `{ _id, supplierId, liquidationCycleId, name, templateName, inventoryFilters, schedule, emailTemplate, rules, stages, donationConfig, isActive, stats }` (Indexed `{ supplierId: 1, name: 1 }` unique for scoped strategy naming and interactive stage-gate timeline visualization).

## Testing Decisions

### Seams for Testing
1.  **API Level (Highest Seam)**: We will write integration tests that hit the Express endpoints.
    - Test that `/api/ingest/upload` correctly handles document upload and responds with a suggested mapping.
    - Test that `/api/inventory/opportunity/:id/pricing/recommend` returns a valid pricing curve.
    - Test the full bidding, awarding, and shipment lifecycle using mocks.
2.  **Sidecar Level**: We will write unit tests for Python services (docling parsing, pricing math solver, matching scoring) using `pytest`.

### Acceptance Criteria
- Testing must cover negative cases (missing fields, expired goods, invalid file formats).
- Performance requirement: Python sidecar must start in under 5 seconds, and API requests (excluding PDF parsing) must return in under 300ms.
- 100% test coverage on core math logic (pricing calculations and score distributions).

## Out of Scope
- Integration with external AWS S3 for B2B document storage (local filesystem storage will be used for uploads).
- OCR extraction from image files (e.g. JPG invoices are not supported; strictly PDF and CSV).
- Real payment processing (all transactions are simulated).
- Live email/SMS notification dispatch (notifications are simulated as dashboard logs/alerts).
- Real-time third-party logistics (3PL) carrier integrations (donation/recycling freight is simulated as a static log timeline; Freight Logistics and Distressed Analytics UI sections are deferred for base release via feature flags `SHOW_FREIGHT_LOGISTICS = false` and `SHOW_DISTRESSED_ANALYTICS = false`, see [ADR 0025](file:///Users/debashisroy/Documents/SpoilerAlert/docs/adr/0025-defer-distressed-analytics-and-freight-logistics-for-base-release.md)).
