# Issue #8: Implement V2 Surplus Inventory Platform (PRD)

> *This was generated by AI during triage.*
> **State:** `ready-for-agent`
> **Category:** `enhancement`

## Problem Statement

The V1 Surplus Inventory Platform demonstrates a functional simulation of messy data ingestion, yield pricing, and buyer matching. However, it lacks production-ready capabilities for real-world enterprise transactional workflows. In ingestion, synchronous PDF/CSV parsing is CPU/RAM-heavy and risks OOM crashes. In transactions, the "1-click Notify & Sell" flow lacks standard B2B negotiation, partial awards, and legal document exchange (POs, BOLs). Furthermore, the platform lacks compliance and traceability under FDA/FSMA regulations (e.g., allergen tracking, lot Batch Records, cold chain temp logs), uses static pricing defaults that don't learn from marketplace activity, and relies on stale, pre-computed snapshots for dashboard analytics.

## Solution

Transition the platform to V2 by implementing:
1. **Asynchronous Ingestion Pipeline**: Leverage LocalStack S3 and SQS to handle file uploads asynchronously, using a Python background worker for heavy Docling parsing that communicates back to Express via a webhook callback.
2. **B2B Negotiation & State-Driven Bidding**: Upgrade the bidding model to support formal counter-offers (unified within chat messages) and partial awards, deducting lot quantities incrementally and auto-generating Purchase Order (PO) PDFs.
3. **FDA/FSMA Compliance & Traceability**: Enforce mandatory Certificate of Analysis (COA) and Batch Record uploads for FDA-regulated products before listings go live, track food allergens to exclude matching buyers, and log cold storage temperatures.
4. **Logistics & Freight Integration**: Track actual carriers, schedule pickup windows, generate Bill of Lading (BOL) PDFs, and enforce dock appointment confirmation before transit.
5. **Real-time Analytics**: Replace static snapshots with live MongoDB aggregation pipelines cached in a fail-safe Redis layer.

## User Stories

1. As a supplier operations manager, I want to upload large product spreadsheets and invoices asynchronously, so that my browser remains responsive during processing.
2. As a supplier, I want to see a progress bar and status indicator for my document ingestion jobs, so that I know when the extraction is complete.
3. As a supplier, I want to configure column mapping templates that save automatically for future uploads, so that I don't have to manually match columns every time.
4. As a seller, I want to negotiate prices and quantities with buyers on an active listing, so that we can agree on mutually beneficial terms before closing a sale.
5. As a seller, I want to accept a portion of a buyer's bid (partial award), so that I can sell the remaining stock to other bidders on the marketplace.
6. As a seller, I want the system to automatically deduct the awarded quantity from the lot's available quantity and auto-reject bids that exceed what is left, so that I don't oversell my inventory.
7. As a seller, I want the system to generate a PDF Purchase Order once a bid is accepted, so that we have an official record of the transaction.
8. As an auditor, I want to ensure that FDA-regulated products cannot be activated or listed without an uploaded Certificate of Analysis and Batch Record, so that the company remains compliant with food safety standards.
9. As a buyer, I want to exclude products containing specific allergens (e.g., milk, soy) from my matching recommendations, so that I don't buy inventory I cannot distribute.
10. As a logistics manager, I want the system to generate a Bill of Lading (BOL) PDF automatically upon bid awarding, so that we have a standard manifest for freight carrier pickup.
11. As a carrier, I want to confirm my scheduled dock appointment before the shipment status transitions to "in transit," so that dock scheduling remains organized.
12. As a compliance officer, I want to view temperature logs for refrigerated shipments, so that I can verify the cold chain was not broken during transport.
13. As an executive, I want to view real-time metrics on distress margins, COGS recovery, and landfill diversion on-demand, so that I can evaluate platform performance using current data.

## Implementation Decisions

* **Asynchronous Ingestion**: `POST /api/ingest/upload` in Express saves raw files to a LocalStack S3 bucket, creates a `DocumentImport` record with status `'queued'`, and publishes a message to SQS. The Python sidecar worker polls SQS, downloads the file from S3, parses it via Docling, and calls Express `POST /api/ingest/callback` to save the results.
* **Negotiation & Awards**: The `Offer` schema is updated with an expanded status enum (`'pending' | 'countered' | 'rejected' | 'partially_accepted' | 'fully_accepted'`) and `awardedQty`. Negotiation comments and financial counter-proposals are unified inside the `messages` array using `proposedPrice`/`proposedQuantity`.
* **PO & BOL Generation**: The backend uses the `pdfkit` library to programmatically generate POs and BOLs, saving the documents to LocalStack S3 and storing their URLs in the `Award` and `Shipment` collections respectively.
* **Allergens & Compliance**:
  * `ProductMaster` schema gets `allergens: [String]`.
  * `Buyer` schema gets `excludedAllergens: [String]`.
  * `InventoryLot` schema gets `fdaRegulated: Boolean`, `temperatureMin: Number`, `temperatureMax: Number`, and `complianceDocs: [ObjectId]` (pointing to `ComplianceDocument`).
  * Listings for regulated products require both a `COA` and `BATCH_RECORD` document uploaded before they can be set to `'active'`.
* **Logistics**: The `Shipment` schema includes new fields: `bolNumber`, `bolPdfUrl`, `carrierName`, `carrierDotNumber`, `pickupWindowStart`, `pickupWindowEnd`, and `temperatureLogs`. Shipment status is updated to include `'confirmed'`.
* **Analytics & Caching**: Pre-computed snapshots are replaced by dynamic MongoDB aggregations on `/api/analytics/summary`. Results are cached in Redis with a 5-minute TTL. Express connects to Redis gracefully and falls back to running raw Mongo aggregations if Redis is offline.

## Testing Decisions

* Tests will be written in `backend/src/tests` using the Jest and `supertest` frameworks, matching the pattern of existing API tests (e.g. `ingest.test.ts`).
* We will mock S3/SQS communication in unit tests, or run integration tests directly against the LocalStack local endpoints when spinning up the services via `docker-compose`.
* High-level endpoints (`POST /api/ingest/callback`, `POST /api/inventory/:id/award`, and `GET /api/analytics/summary`) will be tested for status updates, correct database persistence, schema constraints, and caching fallback behavior.

## Out of Scope

* Integration with actual 3PL carrier APIs (like FedEx/UPS/C.H. Robinson) is out of scope; carrier information will be input manually or mocked using the abstract interfaces.
* Production AWS IAM configuration and real cloud deployment setup; all AWS-facing commands will execute against the simulated LocalStack containers.
